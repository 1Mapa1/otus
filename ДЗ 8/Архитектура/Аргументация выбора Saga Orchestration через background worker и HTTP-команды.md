Решение сделано в рамках домашнего задания по распределённым транзакциям.

Нужно реализовать создание заказа с участием нескольких сервисов:

- `BillingService` — платёж;
- `WarehouseService` — резерв товара;
- `DeliveryService` — резерв доставки;
- `OrderService` — заказ и его состояние.

Если один из шагов не выполнен, уже выполненные действия должны быть отменены.

Для задания важна не только реализация, но и наглядность: должно быть понятно, какой паттерн используется, какие шаги выполняются, где происходит компенсация и как заказ переходит в финальное состояние.
## Выбранный подход

Выбран подход **Saga Orchestration через background worker и HTTP-команды**.

`OrderService` является оркестратором. Он хранит состояние заказа, выполняет шаги Saga и запускает компенсации.

Команды Saga выполняются по HTTP:

```text
BillingService authorize
WarehouseService reserve products
DeliveryService reserve slot
BillingService capture
```

Сама Saga выполняется в `OrderSagaWorker`.

`POST /api/orders` создаёт заказ в статусе `Processing` и возвращает `202 Accepted`. Финальный статус клиент получает позже через `GET /api/orders/{id}`.
### Почему Saga

Создание заказа затрагивает несколько независимых сервисов:  
  
- `BillingService` изменяет состояние платежа;  
- `WarehouseService` изменяет состояние товарного резерва;  
- `DeliveryService` изменяет состояние слота доставки.  
  
У каждого сервиса своя база данных, поэтому `OrderService` не может открыть одну общую локальную транзакцию и зафиксировать все изменения одним `commit`.  
  
При этом по заданию нужно обеспечить поведение "если один шаг не выполнен, откатить уже выполненные изменения". Для этого подходит Saga: процесс разбивается на несколько локальных транзакций, а для каждого уже выполненного шага задаётся компенсирующее действие.
### Почему Orchestration

Orchestration выбран потому, что создание заказа требует общего состояния процесса: текущего шага, уже выполненных действий, нужных компенсаций и финального статуса заказа.

Этим состоянием владеет `OrderService`, поэтому он выступает оркестратором Saga.

При Choreography состояние процесса было бы распределено между сервисами и событиями. Это усложнило бы понимание того, на каком шаге находится заказ, какие действия уже выполнены и какие компенсации нужны при ошибке.

Для домашнего задания важна наглядность проверки, поэтому выбран централизованный вариант: весь процесс виден через `OrderService`, `SagaStep` и статус заказа.

Минус подхода — `OrderService` становится связан с участниками Saga и знает порядок шагов. Этот trade-off принят осознанно.

### Почему HTTP

HTTP выбран для команд Saga, потому что для этого задания достаточно простой request/response-модели: `OrderService` отправляет команду участнику, получает ответ и принимает следующее решение.

Kafka commands/events тоже могли бы использоваться, но потребовали бы дополнительный протокол: command topics, result events, correlation id, ожидание ответных событий и deduplication. Для текущего сценария это усложнило бы реализацию без существенной пользы для демонстрации Saga.

HTTP также проще проверять через Postman: видны запросы, ответы и бизнес-ошибки участников.

Kafka используется только для финальных событий `OrderConfirmed` и `OrderRejected`, потому что уведомления не влияют на результат создания заказа и не требуют синхронного ответа.
### Почему background worker

Saga не выполняется целиком внутри `POST /api/orders`.

Это сделано потому что:

- клиентский запрос не ждёт все межсервисные вызовы;
- состояние Saga можно сохранять после каждого шага;
- после сбоя можно продолжить выполнение;
- технические ошибки можно повторять через retry;
- процесс удобно показывать через polling `GET /api/orders/{id}`.

## Почему не альтернативы

**Two-Phase Commit** требует общего протокола `prepare/commit/rollback` для всех участников. В работе сервисы независимы и взаимодействуют через HTTP, поэтому локальные транзакции с компенсациями подходят лучше.

**Saga внутри HTTP request/response** привязывает весь процесс к одному клиентскому запросу. Для нескольких межсервисных вызовов это увеличивает длительность запроса и ухудшает восстановление после сбоя.

**Saga Orchestration через Kafka commands/events** решает ту же задачу, но требует command topics, result events, correlation id и deduplication. Для линейного сценария заказа это добавляет сложность без необходимости.

**Saga Choreography через Kafka events** убирает центральный оркестратор, но распределяет состояние процесса между сервисами. Для задания важнее явно показать шаги Saga, компенсации и итоговый статус заказа в одном месте.
