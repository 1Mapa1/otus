### Two-Phase Commit

#### Описание

Two-Phase Commit — это подход, при котором распределённая транзакция управляется координатором. На первом этапе координатор спрашивает участников, готовы ли они зафиксировать изменения. На втором этапе он отправляет команду commit или rollback всем участникам.
#### Плюсы

- Даёт атомарный результат распределённой операции: все участники фиксируют изменения или все откатываются.
- Исключает ситуацию, когда один участник успешно зафиксировал изменение, а другой отказался от операции.
- Не требует бизнес-компенсаций после уже выполненных действий.
- Позволяет откатить операцию до финальной фиксации изменений.
- Даёт централизованную точку принятия решения по распределённой транзакции.
#### Минусы

- Требует поддержки `prepare`, `commit` и `rollback` каждым участником.
- Удерживает ресурсы между подготовкой и финальным решением.
- Блокирует завершение операции, если один из участников отвечает медленно.
- Зависит от доступности координатора.
- Зависит от доступности всех участников во время выполнения транзакции.
- Требует дополнительных сетевых обменов между координатором и каждым участником.
- Сложно применяется к долгим бизнес-процессам, потому что ресурсы могут быть заблокированы слишком долго.
- Сложно реализуется поверх обычных REST API без отдельного транзакционного протокола.
### Saga Orchestration внутри HTTP request/response

#### Описание

`OrderService` выполняет всю Saga прямо во время обработки запроса `POST /api/orders`.

Пример последовательности:

```text
POST /api/orders
  -> BillingService authorize
  -> WarehouseService reserve products
  -> DeliveryService reserve slot
  -> BillingService capture
  -> return Confirmed / Rejected
```
#### Плюсы

- Клиент получает финальный результат в ответе на `POST /api/orders`.
- Весь сценарий выполнения находится в одном сервисе-оркестраторе.
- Порядок шагов и компенсаций явно задан в коде оркестратора.
- Оркестратор сразу получает результат каждого шага через HTTP response.
- Не требуется отдельный механизм асинхронного выполнения Saga.
- Не требуется брокер сообщений для команд между участниками.
#### Минусы

- Клиентский HTTP-запрос длится до завершения всей Saga.
- Оркестратор зависит от доступности всех участников во время обработки запроса.
- Timeout клиента может произойти раньше завершения Saga.
- При падении оркестратора во время запроса сложнее продолжить выполнение с места сбоя.
- Повтор клиентского запроса может запустить тот же бизнес-сценарий повторно, если нет идемпотентности.
- Рост количества шагов увеличивает длительность и риск ошибки одного клиентского запроса.
### Saga Orchestration через background worker и HTTP-команды
#### Описание

`OrderService` принимает заказ, сохраняет его в статусе `Processing` и возвращает клиенту `202 Accepted`. Дальше отдельный `OrderSagaWorker` выполняет шаги Saga через синхронные HTTP-команды к сервисам-участникам.

Пример последовательности:

```
POST /api/orders
  -> save order as Processing
  -> WarehouseService resolve products
  -> return 202 Accepted

OrderSagaWorker
  -> BillingService authorize
  -> WarehouseService reserve products
  -> DeliveryService reserve slot
  -> BillingService capture
  -> mark order as Confirmed
```

При бизнес-ошибке worker запускает компенсации и переводит заказ в `Rejected`.
#### Плюсы

- Клиентский запрос не ждёт завершения всей Saga.
- Весь сценарий выполнения находится в одном сервисе-оркестраторе.
- Порядок шагов и компенсаций явно задан в коде оркестратора.
- Состояние Saga можно сохранить и продолжить выполнение после сбоя.
- Оркестратор сразу получает результат каждого шага через HTTP response.
- Технические ошибки можно обрабатывать повторными попытками без повторного клиентского запроса.
- Не требуется брокер сообщений для команд между участниками.
- Подходит для процессов, которые не должны выполняться целиком внутри одного HTTP-запроса.
#### Минусы

- Клиент не получает финальный результат сразу.
- Требуется отдельный механизм получения финального статуса: polling, callback или событие.
- Оркестратор становится центральной точкой управления процессом.
- Оркестратор зависит от доступности участников в момент выполнения каждого HTTP-вызова.
- Требуется хранить состояние Saga между шагами.
- Требуется идемпотентность команд участников для безопасных retry.
- При росте количества бизнес-сценариев увеличивается сложность оркестратора.
### Saga Orchestration через background worker и Kafka commands/events
#### Описание

`OrderService` остаётся оркестратором, но взаимодействует с участниками не через HTTP, а через Kafka. Оркестратор публикует команды, сервисы-участники обрабатывают их и публикуют события-результаты.

Пример последовательности:

```
POST /api/orders
  -> save order as Processing
  -> WarehouseService resolve products
  -> return 202 Accepted

OrderSagaWorker
	OrderService -> AuthorizePaymentCommand
	BillingService -> PaymentAuthorized / PaymentFailed
	
	OrderService -> ReserveStockCommand
	WarehouseService -> StockReserved / StockReservationFailed
	
	OrderService -> ReserveDeliveryCommand
	DeliveryService -> DeliveryReserved / DeliveryReservationFailed
```
#### Плюсы

- Клиентский запрос не ждёт завершения всей Saga.
- Весь сценарий выполнения находится в одном сервисе-оркестраторе.
- Порядок шагов и компенсаций явно задан в коде оркестратора.
- Оркестратор не требует синхронного HTTP-ответа от участника.
- Команды могут быть сохранены в брокере до обработки участником.
- Участники могут обрабатывать команды независимо от времени отправки.
- Состояние Saga можно восстанавливать по сохранённому состоянию оркестратора и событиям-результатам.
- Повторная обработка сообщений может быть контролируемой через inbox/deduplication.
#### Минусы

- Требуется брокер сообщений.
- Требуется проектировать команды и события-результаты отдельно.
- Требуется correlation id для связи команды, ответа и конкретной Saga.
- Финальный результат шага не приходит как обычный return/HTTP response.
- Нужно отдельно обрабатывать случаи, когда ответное событие не пришло.
- Требуется идемпотентность обработки сообщений.
- Требуется защита от повторной доставки сообщений.
- Отладка цепочки выполнения сложнее, чем при прямых HTTP-вызовах.
- Оркестратор всё равно знает порядок шагов, контракты команд и компенсирующие операции.

### Saga Choreography через Kafka events
#### Описание

В этом варианте нет центрального оркестратора. Каждый сервис реагирует на события и публикует следующее событие. Бизнес-процесс складывается из цепочки реакций сервисов.

Пример последовательности:

```
POST /api/orders
  -> WarehouseService resolve products
  -> publish OrderCreated
  -> return 202 Accepted

OrderCreated
  -> BillingService authorizes payment
PaymentAuthorized
  -> WarehouseService reserves products
StockReserved
  -> DeliveryService reserves slot
DeliveryReserved
  -> OrderService confirms order
```
#### Плюсы
- Нет центрального оркестратора процесса.
- Сервисы не вызывают друг друга напрямую для выполнения Saga.
- Каждый участник реагирует на событие и публикует результат своей операции.
- Добавление нового подписчика на событие не требует изменения отправителя события.
- События могут быть сохранены в брокере до обработки подписчиками.
- Участники могут обрабатывать события независимо от времени их публикации.
- Нет одного сервиса, который содержит весь порядок шагов Saga.
- Подходит для процессов, где реакций на событие много и они не всегда образуют строгую линейную цепочку.
#### Минусы

- Нет единого места, где явно задан весь порядок выполнения Saga.
- Текущее состояние процесса нужно собирать из событий и состояний разных сервисов.
- Компенсации распределены между участниками.
- Изменение порядка шагов может требовать изменений в нескольких сервисах.
- Требуется correlation id для связи событий с одной Saga.
- Требуется идемпотентность обработчиков событий.
- Требуется защита от повторной доставки сообщений.
- Отладка цепочки выполнения сложнее, чем при централизованном оркестраторе.
- При ошибке одного участника не всегда очевидно, какой сервис должен инициировать следующий компенсирующий шаг.

| Saga Orchestration через background worker и HTTP-команды | Централизованный оркестратор | HTTP | После возврата `202 Accepted` | Сохранение состояния и продолжение после сбоя | Жёсткая зависимость бизнес-процесса от оркестратора |
| Saga Orchestration через background worker и Kafka commands/events | Централизованный оркестратор | Kafka commands/events | После возврата `202 Accepted` | Асинхронное взаимодействие без ожидания HTTP-ответа | Высокая сложность корреляции команд и событий |

## Итог

Все перечисленные подходы могут быть применены к задаче распределённой транзакции, но они дают разные trade-off'ы.

В данной работе выбран подход **Saga Orchestration через background worker и HTTP-команды**.
